# 委托协议（在线模型 ↔ 本地 27B）

> 一句话：**在线模型当编排器，27B 当执行器，机器检查当第一道筛，定稿权在用户。**
> 实现：`src\qwen_delegate.py`；自测：`src\test_qwen_delegate.py`（不调模型，几秒跑完）。

## 1. 为什么有这一层

27B 有 14–16 tok/s 的速度，也有它自己的毛病：爱改写、爱解释、爱补没被要求的内容，JSON 偶尔不合法。直接让它写正文等于把风险引进来。所以把它关进一个**只做被指派子任务**的壳里：

```text
在线模型（我）
  ├─ 判断：这活该拆成什么子任务（校对？续写？核查？改写？）
  ├─ 函数调用 qwen_delegate(task_type, payload)
  │     ├─ 选提示词 + 项目硬规则
  │     ├─ 调本地 27B（think=false，必要时升档）
  │     ├─ 跑机器检查（可复现、不看模型心情）
  │     └─ 硬检查不过 → 带失败原因重问一次（think 升到 low）
  └─ 拿回 result + checks + review
        ├─ review 有内容 → 我逐条判断
        └─ 最终稿仍由我写、由用户定
```

分工原则：**机器只负责“能算出来的错”**（丢了数字、改了九成内容、引文对不上原文、输出空）；**语义好坏归在线模型**；**定稿权归用户**。

## 2. 调用契约

一次调用 = 一个 JSON 对象：

```json
{"task_type": "proofread", "payload": {"text": "……"}}
```

返回信封：

| 字段 | 说明 |
|---|---|
| `ok` | 全部 hard 检查是否通过 |
| `result` | text 任务返回字符串；json 任务返回已解析的对象 |
| `raw` | 模型原始输出（排查用，别直接信） |
| `checks[]` | 每项 `{id, ok, level, detail}`，level 是 `hard`/`soft` |
| `review[]` | **给在线模型看的待判断点**；空数组=机器这关没问题 |
| `usage` | 耗时、token、tok/s、num_ctx、逐轮 attempts |
| `model` / `ts` | 模型名与时间戳 |

退出码：`0` 通过；`2` 有硬检查失败或调用失败（判定“需要我复核”，不代表结论错）。

## 3. 六个任务类型

| task_type | 干什么 | 输出 | 硬检查 |
|---|---|---|---|
| `proofread` | 只改错别字和半角→全角标点 | text | 改动比例≤18%、数字不丢、段落数不变 |
| `continue` | 按前文续 1–3 句 | text | 字数上限、不出现俯视/解释腔 |
| `fact_check` | 设定核查，逐条给 supported / contradicted / absent | json | 有 `findings`、**引文逐字回查原文** |
| `span_edit` | 挑 1–3 句给替换句 | json | 有 `pairs`、`old` 必须逐字取自原文 |
| `event_card` | **把资料整理成一张事件卡**（标题/时间/地点/主体/起因/经过/结果/影响 + 引文） | json | 有 `event`、引文逐字回查、不许出现推断性表述 |
| `event_detail` | **详细事件资料**（背景/时间线/主体/事实/数字/争议/原话/未解问题/写作用途） | json | 内部三段委托后合并；引文全量回查、引文≥5 条 |
| `rolling_summary` | **分段滚动摘要**（模型自己切段，逐段摘要，每段只带上一段作前文） | json | 段数 3–12、每段独立（无“如前所述”）、引文逐字 |
| `flag` | **段落标改**（3B 小模型逐段判“改/不改”） | json | 段数>0、标签明确；跑前自动卸载 27B 腾显存 |
| `vision` | **图片转文字**（ocr 逐字转写 / describe 描述） | text | 非空、不许拒答 |
| `img_translate` | **图片英译中**（英文转写 + 中文翻译，附逐行对照） | json | 英文/中文都非空，行数对齐（soft） |
| `translate` | **英译中**（纯文本英文 → 中文） | text | 非空、数字不丢、译/源字比合理 |
| `ask` | 通用问答，不带项目规则 | text | 非空、无套话 |
| `custom` | 自己写 instruction，自选检查 | text/json | 由 `checks` 指定 |

**任务类型可以直接用中文模式名**（`--task 滚动摘要`、`--task 事件卡`、`--task 校对`），大小写和前后空格会自动归一；中文名与英文 id 的对照见 术语表.md 第 6 节。

检查项可组合：`nonempty` `no_meta` `no_pov` `no_explain` `no_guess` `length_max` `minimal_edit` `keep_numbers` `keep_paragraphs` `schema` `quotes_in_source` `all_quotes_in_source` `min_evidence` `old_in_source`。

`all_quotes_in_source` 递归查任意层级的 `quote`/`evidence`（事件资料字段深，顶层检查不够用）；`min_evidence` 要求引文条数达标，防止输出空壳。

`hard` 失败 → 触发一次升档重试，仍失败则 `ok=false`；`soft` 失败 → 只进 `review`，不重试。

## 4. 怎么调用

```powershell
$env:OLLAMA_MODELS='C:\path\to\ollama-models'   # 模型在 F 盘，改动前开的终端要显式带
$env:PYTHONIOENCODING='utf-8'

# 看有哪些任务类型
.\.venv\Scripts\python.exe src\qwen_delegate.py --list

# 给 function-calling 用的工具定义（OpenAI tools 格式）
.\.venv\Scripts\python.exe src\qwen_delegate.py --tools-json

# 干跑：只拼 prompt，不花显卡
.\.venv\Scripts\python.exe src\qwen_delegate.py run --task proofread --text-file 02_文档\x.txt --dry-run

# 实跑（推荐走文件，避免 PowerShell 吞引号）
.\.venv\Scripts\python.exe src\qwen_delegate.py run --task proofread --text-file 01_正文\草稿\第018章草稿.txt
.\.venv\Scripts\python.exe src\qwen_delegate.py run --task event_card --text-file 02_文档\资料.md
.\.venv\Scripts\python.exe src\qwen_delegate.py run --task fact_check --payload-file payload.json
```

`--payload-file` 内容形如 `{"text":"…","question":"…"}`。也支持 `call -` 从 stdin 读整份 `{task_type, payload}`。

**两个已踩过的坑**：PowerShell 传 `--payload-json '{"a":"b"}'` 会把双引号吞掉导致 JSON 解析失败，用文件或 stdin；Windows 下 `Set-Content` 可能写 BOM，工具已按 `utf-8-sig` 读，但你手写的 payload 尽量存成无 BOM。

## 5. 使用纪律

1. **它是候选，不是定稿**。`ok=true` 只说明过了机器关，语感、设定、剧情仍要我核、要用户点头。
2. **不自动改稿**。委托结果先给我看，改动落到修订稿前要和用户确认；用户正在改文件时不动。
3. **`review` 非空先读 review**，别直接抄 `result`。
4. **超长先分块**：`pick_ctx` 在 4096/8192 装不下时会直接报错（约 7,000 tokens 以上），按场景切段再委托，别指望它一次吃完一章。
5. **thinking 会吃生成预算**：`think=low` 时 `num_predict` 要给足，否则正文可能是空的（工具已按任务给默认值，不要随意调小 `--max-tokens`）。
6. **卡片仍走 `qwen_card.py`**：章节卡片有分块、升档、引文回查的专用逻辑，别用 `custom` 重造。

## 6. 实测（2026-10-23，第 18 章真实草稿）

| 任务 | 结果 | 耗时 | 检查 |
|---|---|---|---|
| proofread | 半角→全角、引号统一，一字未改 | 21.0s | 改动 11.1%，数字/段落保留，0 次升档 |
| span_edit | 挑出“也不知道具体来说什么顺序……”并收紧 | 6.2s | old 逐字命中原文 |
| fact_check | 学费 250000 / 住宿 12000 / 饭卡预存制；开学日期判 `absent` | 12.0s | 引文 3/3 回查通过 |

三次都是首轮通过，没触发升档。`absent` 那条尤其关键：原文确实没写开学日期，它没有拿常识去补。

### 第二组：把 6,400 字问答记录整理成事件卡（custom + JSON）

资料：`关于中国的新教神学问题讨论.docx`（四轮问答，6,423 字），ctx 8192，`checks = schema + quotes_in_source + no_guess`。

| 跑次 | 耗时 | 机器检查 | 我的复核结论 |
|---|---|---|---|
| 第一跑 | 54.7s / 520 tok | 全过（引文 3/3） | **有 3 处实质错误**：`time` 自己承认“推断”、`place` 是推的、`cause` 与 `process` 因果倒置 |
| 第二跑（收紧指令 + 加 `no_guess`） | 23.3s / 370 tok | 全过 | 事实层干净了；仍有 `cause`= `process[0]` 重复、`impact` 复述 `result` |
| 第三跑（换成六轮完整版 8,737 字） | 40.7s / 341 tok | 全过（引文 3/3） | 选中同一事件；**同一角色错位第三次复现**：`cause` 写成本身、`impact` 复述 `result` |

三次跑下来，27B 在“事件卡”上有稳定的角色错位倾向：**`cause` 容易被填成事件本身，`impact` 容易被填成 `result` 的复述**。这不是随机波动，改指令只能缓解不能根治；这类问题只能靠在线模型逐字段改写，或者拆成“先抽骨架、再填字段”的两步委托。

这一组说明**机器检查只能挡“能算出来的错”**：格式、引文、字数、禁用词。像“因果倒置”“字段间重复”这类语义问题，必须由在线模型复核——所以委托层的定位是**半成品 + 检查单**，不是成品。

### 第三组：详细事件资料（`event_detail`，三段委托）

同一份 8,737 字资料，要输出 10 个分节。**单次生成试了四次全部失败**：输出被截断、JSON 在第 120～240 行断掉，每次还白白触发 3 次重试（最贵一次烧了 890 秒）。改成三段后一次通过。

| 段 | 内容 | 耗时 | 输出 |
|---|---|---|---|
| A | event / background / timeline / actors | 83.4s | 988 tok |
| B1 | facts / numbers | 73.0s | 873 tok |
| B2 | disputes / quotes / open_questions / writing_use | 76.2s | 665 tok |
| 合计 | 三段串行 + 合并校验 | **232.6s** | 2,526 tok，**引文 32/32 回查通过** |

结论：**长输出不是加预算能解决的，要拆段**。另外 A 段首轮 3 条时间线引文是改写不是逐字，靠 `--rounds 2` 带着失败原因重问一次才修好——所以默认重试值得开。

### 第四组：分段滚动摘要（`rolling_summary`）

8,885 字一次读完再吐摘要会撞输出上限；反过来“先摘要再合并”又会在合并时再撞一次。解法是**让模型自己切段，逐段摘要**：

1. 原文按段落编号交给模型，它返回 `{"sections":[{"from":1,"to":11,"title":"..."}]}`；
2. 校验必须从 1 连续覆盖到末尾（不重不漏），不合法就退回按字数均分；
3. 逐段摘要，**第 N 段只带第 N-1 段的摘要作前文**——不递归、不累积、不带更早的段；
4. 每段摘要必须独立成文：命中“如前所述／上一段／前文／综上”即扣分。

实测（同一份六轮资料）：

| 项 | 结果 |
|---|---|
| 切段 | 模型切成 6 段（718–1,931 字/段） |
| 耗时 | 132.9s（1 次切段 + 6 次摘要） |
| 压缩 | 摘要合计占原文 **11.1%** |
| 检查 | 6 段 × 5 项全部通过，引文 6/6 逐字命中 |

已知代价：相邻段会有轻微重复（第 2 段把第 1 段的结论又带了一句），这是“只带一段前文”的必然副作用，换来的是每段都能独立阅读。要压重复就把前文块删掉，代价是段与段的转折会生硬。

## 7. 和现有工具的关系

- `qwen_client.py`：底层 HTTP 客户端（重试、JSON 纠正、写 `06_日志\qwen_calls.jsonl`）。委托层复用它，不另发请求。
  **2026-10-25 新增 `schema=` 参数**：传 JSON Schema 就走 Ollama 的结构化输出（约束解码），
  形状不对的 token 在采样阶段即被禁止——比"`format: json` + 事后校验"可靠一个档，实测 27B 可用。
- `qwen_card.py`：章节卡片专线，逻辑更重（分块、diag、ladder）。
- `qwen_delegate.py`：通用子任务委托，**带检查单**，是给在线模型调的。
- `flag_paragraphs.py`：3B 段落 flagger，判断“这段用户会不会改”，和委托层互补。

## 8. 派活给本地模型写代码（2026-10-25 起）

用户明确要求：**开发任务不要在线模型全包**，能拆就拆给本地 27B。可行的做法是“契约 + 用例 + 验收”，
四件套都在 `src\_试作\`：

| 文件 | 角色 |
|---|---|
| `spec_*.txt` | 契约：数据结构、每个函数的输入输出、边界情况、错误消息原文 |
| `fixture_*.py` | 固定用例：故意覆盖空串、超长、重复、类型错、块列表/字符串两种形态 |
| `test_*.py` | 验收：逐条 PASS/FAIL，退出码非 0 表示不过 |
| `delegate.py` | 通用派活器：`--spec <契约> --out <产物> [--note 反馈] [--check <验收命令>]... [--max-rounds N]`，另可 `--fix` 还原转义 |
| `delegate_checks.py` | 契约 lint（约束清单/散落约束/验收节）+ 验收反馈：`extract_constraints` / `lint_spec` / `build_feedback` / `run_checks` |

**P-008 修复（2026-10-25）**：多条硬约束必须集中写进 `## 约束清单` 并按编号列出；
`delegate.py` 先 lint 契约，再用 `--check` 跑验收命令，未过则把失败输出作为反馈重派（默认最多 2 轮）。
smoke：`clamp`（`bool` 抛 TypeError + `lo>hi` 返回 `lo` 两条不相邻约束）首轮通过（3.5s / 56 tok / 0 重派）。

**铁律：验收测试必须先跑过一个参考实现**（`ref_*.py`），全部 PASS 才说明尺子本身是准的；
否则可能出现“27B 没错、是我断言写错”。2026-10-25 就先被自己的测试坑过两次（超长单元其实没超长、小块阈值算错）。

## 9. 在线模型自用任务类型（`impl_audit`）

§3 的任务类型都是**派给本地 27B** 的。有一类活外包不出去——"查业界怎么做 + 把我们自己的实现拆成功能逐个校对"，
需要联网查证和工程判断，只能由在线模型做。它现在也是一个正式任务类型，规程在
[审查规程](审查规程.md)，术语见 术语表 §6.1。

| 项 | 值 |
|---|---|
| task_type | `impl_audit`（实现审查） |
| 执行者 | 在线模型；**不进 `qwen_delegate`** |
| 产物 | `02_文档/审查/<日期>_<主题>.md` |
| 硬检查 | `python src/audit.py check <报告>`：六小节、≥5 功能行、判定 A–F、提案三列、证据有代码块、收尾有问题清单动作 |
| 收尾 | 结论回填流程文档 + 问题清单 add/close |

**与 §8 的分工**：`impl_audit` 负责"判断该不该改、改成什么样"，§8 负责"把改法派给 27B 实现"。
两者衔接点就是审查报告的「修复提案」表——提案的验收列直接变成下一轮派活记分牌。

速度约 19 tok·s⁻¹（`json_mode=False` 的纯文本输出，比 JSON 模式快）。

### 契约写到什么粒度

给到“数据结构 + 边界清单 + 期望的错误消息原文”，它就能一次过。含糊的地方会立刻变成 bug：
首版 26 条里唯一没过的是 `validate_state` 的第 4 条——它只查了 `内容` 键存在，没查非空。
把失败原文喂回去（`--note`），142 秒后自己修好，且没改坏别的函数。

### 四个踩过的坑

1. `qwen_client.chat()` 返回的 `Call` 属性是 `.text`，**不是 `.content`**。写错时 `hasattr` 为假、静默走
   `str(res)` 分支，落盘的是 `repr(Call(...))` 一整行转义文本，看起来像“模型输出坏了”。
2. **围栏提取不能用正则** ```` ```(.*?)``` ````：模型常会在正文里提到 ```` ```json ````，正则会在那里提前闭合，
   把内容截断（实测只剩 144 字符）。改成“第一行以 ``` 开头的行 → 最后一行内容恰为 ``` 的行”。
3. 模型爱**把整个模块写两遍**（第一份往往是半成品）。取最后一份，或落盘后先做语法检查。
4. 新文件在 F 盘（exFAT）用 `write` 会 `EISDIR`：先 `New-Item -ItemType File` 占位，再写（同 §开发约定 坑表）。
