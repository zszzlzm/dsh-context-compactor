# 开发约定

> 这个仓库里写脚本、跑模型、动文件时的固定规矩。踩过的坑都在这。
> 配套：[委托协议](委托协议.md)、委派规则、分镜工作流、生图部署方案。

## 1. 环境事实（先认准，别猜）

| 项 | 值 |
|---|---|
| 项目根 | `/path/to/your/workspace` |
| Python | 项目 `.venv`（3.12 + torch 2.11+cu128） |
| 生图运行时 | `C:\path\to\aigc\ComfyUI_windows_portable\`（自带 Python 3.13 + torch 2.14+cu130，**独立**，勿混装） |
| Ollama 模型 | `C:\path\to\ollama-models`（靠用户级 `OLLAMA_MODELS`） |
| 服务端口 | Ollama `11434`，ComfyUI `8188` |
| CPU | i5-14600KF，14 逻辑核无超线程：P 核 0–5，E 核 6–13 |

**Ollama 不会自己起来**（2026-10-25 隔夜实测）：机器重启或长时间空闲后 `11434` 直接拒连
（`WinError 10061`），跑任何本地模型前先确认，不要以为是代码坏了：

```powershell
$env:OLLAMA_MODELS='C:\path\to\ollama-models'
Start-Process (Join-Path $env:LOCALAPPDATA 'Programs\Ollama\ollama.exe') -ArgumentList 'serve' -WindowStyle Hidden
Start-Sleep -Seconds 6
(Invoke-RestMethod 'http://127.0.0.1:11434/api/tags' -TimeoutSec 10).models.name
```

**驱动已能自己处理这件事**（2026-10-25）：`qwen_client.ensure_service()` 先 `GET /api/tags` 探活（1 s），
失败则尝试拉起 `ollama serve` 并轮询 ≤15 s；压缩管道在读取日志前调用它，失败直接退出码 2、不写任何产物。
客户端对"连接被拒"**不再重试**（3.06 s 内抛带启动命令的 QwenError，修复前 18.11 s）。
手工命令仍保留——自动拉起分支尚未真机验证（P-056），开机自启仍是更稳的做法。

**会话日志是 zstd 多帧 JSONL**：`~/.dsh/sessions/<工作区哈希>/session-<uuid>/session.v4.jsonl.zstd`，
单帧 `decompress()` 只能解出开头，必须 `stream_reader(fh, read_across_frames=True)`；
`.venv` 里已装 `zstandard`（标准库到 3.14 才有 `compression.zstd`）。

**DSH 的默认 compose 可以直接读，不用猜**：`app.asar` 里的 `dsh/node_modules/@deepseek-ai/<bundle>/cordis.patch.yml`
就是各 bundle 挂载的插件与参数。读法——Electron 二进制设 `ELECTRON_RUN_AS_NODE=1` 当 node 用，
而且它的 `fs` 原生认 `.asar` 内部路径（`fs.readdirSync('<app.asar>/dsh', {recursive:true})`）。
现成工具：`src\_试作\asar_ls.js`。

```powershell
$env:ELECTRON_RUN_AS_NODE='1'
& 'C:\Users\<you>\AppData\Local\Programs\DeepSeek Harness\DeepSeek Harness.exe' `
  'src\_试作\asar_ls.js' '<...>\resources\app.asar' --walk 'cordis.patch.yml'
```

2026-10-25 用它确认过的默认值：`tool-result-pruner` 默认就挂着（`thresholdChars 8192 / headChars 4096 /
tailChars 1024`），`spill-policy.maxInlineTokens = 12500`——所以"要不要开 pruner"这个问题本身是多余的，先查配置。

**评估/对照类调用必须可复现（2026-10-25，P-013）**：`temperature` 只控制采样阶段，
logits 本身会受浮点非结合性、num_ctx 变化、并发批次影响。要"同参数重复跑结果一致"，三件套缺一不可：

| 参数 | 取值 | 说明 |
|---|---|---|
| `temperature` | 0（贪心）或固定值 | 0 时 seed 实际不起作用 |
| `seed` | 固定整数（评估类用 42） | 实测只加 seed 就能把 3 种输出收敛成 1 种 |
| `num_ctx` | 同一任务固定同一个值 | 不同 num_ctx 会改变数值路径 |

用法：`chat(..., deterministic=True)` 等价于 `temperature=0, seed=42`（`num_ctx` 仍需调用方传固定值）；
调用日志现在记录 `temperature` / `seed` 两个字段，便于事后复现。
并发也是变量：评估时保证**单请求串行**，不要与其他任务同时跑（Ollama 的并发槽会改变归约顺序）。

**CPU 功耗是能读的**（2026-10-25 实测，推翻我之前的"读不到"）：Windows 自带 PDH 计数器
`\Energy Meter`，底层是 Intel RAPL，**不需要管理员权限、不需要装任何软件**。

```powershell
# 毫瓦 → 瓦；本机空闲 ~40W，满载 ~180W（PL2 181W），单位已验证
[math]::Round((Get-Counter '\Energy Meter(rapl_package0_pkg)\Power').CounterSamples[0].CookedValue/1000, 1)
Get-Counter '\Energy Meter(*)\Power'   # 实例：rapl_package0_pkg / _pp0(cores) / _dram(本机恒 0) / _total
```

GPU 功耗用 `nvidia-smi --query-gpu=power.draw,power.limit --format=csv,noheader`（RTX 5070 Ti：30–36W 空闲，上限 300W）。
**当时误判的原因**：我去查 WMI（`Win32_Processor` 确实没有功率字段）就下了结论，没试 PDH 计数器——断言前没做实验，老毛病。

**跨项目复用**：文章项目没有自己的 venv，统一调 `/path/to/your/workspace\.venv\Scripts\python.exe`。

## 2. 显存互斥（最容易忘）

三块模型两两不能共存，**必须先清场再跑**：

| 要跑 | 先做 |
|---|---|
| 27B（Ollama） | `POST http://127.0.0.1:8188/free {"unload_models":true,"free_memory":true}` 释放 ComfyUI |
| 生图（ComfyUI） | 调 `qwen_flag3b.unload_27b()`（`qwen_img.py` 已内置） |
| 3B flagger | 同上，卸 27B |

**实测事故**：ComfyUI 占着显存跑 27B，`llama-server` 崩在 `failed to allocate buffer of size 4273332736`。

## 3. 文件写法

| 坑 | 现象 | 规矩 |
|---|---|---|
| 新建文件 | 写入工具报 `EISDIR: illegal operation on a directory, link '.xxx.<pid>.<uuid>.tmpdir\xxx.tmp' -> 'xxx'` | **不是路径错，是 F 盘 exFAT 不支持硬链接**。`write` 工具用「同目录临时文件 + `link()`」原子发布，exFAT 上 `link` 不存在，libuv 还把这个失败错报成 `EISDIR`。**规律：新文件必失败，已有文件可覆盖**（走 rename 分支）。绕法三选一：① `New-Item -ItemType File` 建占位再写；② 让 Python 脚本直接写（不经 `link`）；③ 写到 C 盘（NTFS）再拷。**不要换路径反复试**——2026-10-25 我连试三个路径才发现 |
| 中文 `.ps1` | Windows PowerShell 5.1 按 GBK 读，乱码报错（`Unexpected token '浠?8'`） | 存 **UTF-8 带 BOM**。**`edit`/`write` 工具改文件会把 BOM 丢掉**，改完必须补回；`check_layout.py` 的「PS编码」一项会自动拦 |
| 工具读文件 | 带 BOM 的 JSON 解析失败 | 一律 `encoding="utf-8-sig"` |
| GBK 控制台打印 `↔` | `issues.py relate` **数据已写盘**，随后在 `print(已关联 … ↔ …)` 崩 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2194'`，退出码非 0 但清单其实已改好 | **已修（P-066）**：`issues.py` 入口调用 `console_compat.configure_stdio()`，把 stdout/stderr 强制为 utf-8 + errors=replace；新工具输出 Unicode 符号时同样先调它。别因为 traceback 以为没生效 |
| GUI 宿主 spawn 控制台程序 | 插件/Electron 用 Node spawn `python.exe` 时，Windows 会新建 Windows Terminal 窗口（标题 `Default:<路径>`，`Ctrl+Alt+1` 是 Terminal 提示）；**ConPTY 下窗口属于 Terminal，`GetConsoleWindow/ShowWindow` 藏不掉** | **启动器统一用 `pythonw.exe`**（GUI 子系统，创建时就不分配控制台；管道下 stdout/stderr 可正常捕获，实测 `GetConsoleWindow()=0`）。改 `index.js` 默认值和 `cordis.patch.yml` 两处，重启宿主生效；后台 detached spawn 仍保留 `CREATE_NO_WINDOW` 兜底 |
| PowerShell 传 JSON | 双引号被吞，JSON 解析失败 | 走 `--payload-file` 或 stdin |
| PS 里改 Python 文件 | `\n` 写成字面量 | 用 python 脚本改文件，别用 PS 字符串替换 |

**`EISDIR` 的根因出处**（2026-10-25 联网查到并本机验证）：

- 官方讨论 [#5704](https://github.com/deepseek-ai/deepseek-harness/discussions/5704)：`write` 在 `createIfAbsent` 分支用「临时文件 + `link()`」发布，exFAT/FAT32 没有硬链接，`link` 必失败；libuv 把 `WinError 1` 错映射成 `EISDIR`（所以报“目标是目录”，其实目标根本不存在）。
- 本机验证：`Get-Volume` → F 盘 exFAT；`New-Item -ItemType HardLink` → “指定路径不支持硬链接”。
- 这就是为什么 `素材缺口.md` 能直接写（已存在文件走 rename），而 `扶梯人流.md`、`_judge_regress.py` 这类新文件必失败。

## 4. 后台任务

- `Start-Job` 的作用域绑定在**当前 pwsh 进程**，命令结束即被杀 → 用受管后台任务。
- `Start-Process` 重定向日志时**目录必须先存在**，否则进程起不来。
- 长时间服务（ComfyUI / Ollama）用独立进程启动，日志写 `C:\path\to\aigc\logs\`。

## 5. 调用与预算

| 规则 | 原因 |
|---|---|
| JSON 输出要按“字段数 × 条数”估预算，不按字数 | 撞上限不报错，只吐半截 JSON |
| 单次输出超过 ~2,500 token 的任务，先考虑拆段 | 实测 10 分节必截断 |
| 硬检查失败最多重试 1 次 | 第 3 次仍在同一失效模式里 |
| 多产物必须记来源文件名 | 实测取错图是**静默**的 |

## 6. 文档维护

- 文档分类：`写作规范/`（设定与文风）、`工具与流程/`（怎么干）、`归档/失败项目/`（不用的方案）。
- 术语表与代码的同步由 `src\check_glossary.py` 校验，改代码后跑一次。
- **同一份信息只写一处**，其他地方用链接指过来。

## 8. 数据下载与中间产物（2026-10-24 实测）

| 教训 | 现象 | 规矩 |
|---|---|---|
| **候选图必须按 URL 哈希命名** | 候选链接换了，但 `c01.png` 已存在 → 跳过下载，反复判旧图，白跑三轮 | 下载名用 `c{i:02d}_{md5(url)[:8]}.ext` |
| **模型输出先落盘再解析** | 解析逻辑一出错就要重新调模型，一次几分钟 | 每次调用把原始信封写进 `_工作区/<名>_原始输出.json`，解析失败可 `--from-raw` 复用 |
| **提示词长度上限按实测调** | 加了元素清单后超 560 字被自检卡住 | 当前上限 640 字；超了先砍元素条数，不要砍机位 |
| **外部图源要看 Referer** | 花瓣图链直下返回 0 字节 | 请求头带 `Referer: https://huaban.com/` |
| **花瓣多词查询返回空** | `地铁站 中庭 俯拍` → 0 条 | 用短词（`地铁口`、`扶梯`）再逐个 append |
| **图床扩展名不可信** | 大量 `.jpg` 实际是 webp，`read_image` 和 ComfyUI `LoadImage` 都报格式不符，60 张里一半是假的 | `collect_refs.py` 现在下载后一律用 PIL 转真 JPEG 再落盘，文件名固定 `.jpg`；历史图用 PIL 批量重存 |
| **判分不能开放打分，要按清单核对** | 老 `judge()` 的 prompt 写着“只看它是不是这种地方、有没有可借鉴的结构/光线”——等于叫模型去找优点，条目卡的禁止项又根本没传进去。结果 20 张里过 19 张，地下车库、哥特烛光、游戏截图全 0.90+ | `judge()` 改成读条目卡的「固定描述＋禁止项」当验收清单：先逐条核对题材/视角/画风，再让它**只列出画面里确实出现的禁止项**（列 0 条是正常的），最后 `normalize()` 按硬规则压分。回归见下 |
| **禁止项让模型逐条判 hit，它会全勾 true** | 改成 `{"rule":..,"hit":true/false}` 逐条输出后，一张完全正常的图也把 9 条全标成命中 | `bans` 是**命中列表**不是检查表：只列真的出现在画面里的，并在 prompt 里写明“多数正常的图应该列 0 条，不要为了显得严格硬凑” |
| **条目卡的禁止项就是判分清单** | 旧卡只写“窗户/暖黄/动漫”，车、车位标线、3D 渲染都没写 → 判分当然放行 | 每翻车一次就往卡里补一条：`地下大厅照明` 补了车辆/车位标线/车库坡道/渲染/古典；`枢纽中庭俯拍` 补了渲染概念图/水印/商场卡通装置 |
| **判分是初筛，人眼复核不能省** | 即便按清单判，27B 对“视角”“画风”这类整体判断仍不稳 | 入 `参考/` 前人眼看一遍；不对的移进 `_候选/人工剔除/`，理由写进 `参考清单.md`（重跑脚本会保留这一段） |
| **外部图源补不上时的兜底：本地生成构图板** | 花瓣搜不到“俯拍多层枢纽大厅”（只出概念插画、海滨风景） | 用 `qwen_img.py` 按镜头描述生成结构板，存进 `参考/` 并在 `参考清单.md` 标注「本地生成·仅作结构参考」，不当实拍素材用 |
| **参考图优先序要能指定** | `参考/` 里按文件名排序取首张，新加的图永远排在旧图后面 | 需要当首选图的，文件名以 `01_` 开头（如 `01_生成_俯拍结构板_B.jpg`），数字前缀排在 `c*` 之前 |

## 9. 脚本活跃度

`src/` 里同时存在**现役脚本**和**归档项目的训练脚本**（`train_critic_*`、`make_*_data`、`eval_*` 等）。
后者属于已归档的“三料/影子写手”方案，不再维护、不必写进文档；判断标准是看 `02_文档/归档/失败项目/README.md`。
