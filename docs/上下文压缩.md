# 上下文压缩（按轮增量）

> 目标：把"上下文快满了就一次性把历史压成一篇"换成"每轮结束就地把这一轮压成结构化状态"。
> 配套：[委托协议](委托协议.md) §8（怎么把实现派给本地模型）、[开发约定](开发约定.md) §1（环境事实）。

## 1. 为什么不用默认压缩

DSH 自带的 `dsh-compaction-basic` 是**一次 LLM 调用把所有 shadowed 历史压成一篇检查点**。它的
prompt 模板（8 段：`Primary Request` / `Files and Code` / `Errors and Fixes` / `Pending Jobs` /
`Next Step` / `Critical Context`）本身是好的，粗糙来自运行方式：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 整段历史一次读完（150k token 也照读） | 中段被稀释，只留下"大概做了什么" |
| 2 | 输入不瘦身：推理内容、图片、几十万字的工具结果原样送进去 | 噪声淹没信号 |
| 3 | 一次性生成 8 段 | 越靠后的 section 越省字（注意力衰减），`Critical Context` 最水 |
| 4 | 零机器校验 | 路径拼错、数字丢一位、文件漏记，没人查 |
| 5 | 不可逆 | 漏掉就真没了，没有第二次机会 |

## 2. 设计（五层）

```
会话事件流（zstd JSONL，按 seq 增量）
  │
  ├─ L0 瘦身      头尾保留 / 错误优待 / 去重 / 过期淘汰 / 用户消息不截断   [代码]
  ├─ L1 锚点      六类逐字抽取（路径/编辑/CMD/ERR/要求/CALL），结构化优先   [代码]
  ├─ L2 分段摘要  一轮切块，逐块摘要，每块带上一块摘要作前文       [27B]
  ├─ L3 变更集    上一版状态 + 本轮摘要 + 锚点 → 只输出"变化"（schema 约束解码）  [27B]
  ├─ L4 校验      摘要 5 项 + 状态 5 项，不过就带原因重试一次      [代码]
  └─ L5 回收      先按 anchor_norm 合并重复锚点，再超预算把冷数据剪切进归档，守恒校验后写盘  [代码]
```

关键取舍：

- **只写变化，不改写整篇**。L3 输出的不是新状态，是 `changes` 变更集；合并由 `apply_changes()` 做。
  这样模型每轮只做小编辑，不会越写越抽象。
- **锚点 append-only**。路径、命令、数字、错误串由代码逐字抽取，只能新增，`validate_state()` 会报"锚点丢失"。
  L3 只对新增锚点按 `anchor_norm` 去重；L5 回收时再把历史归一化重复合并（未引用的重复归档、被引用的保留），
  `validate_state(..., warnings=[])` 对归一化重复只记软警告。
- **作废要显式**。"这个决定不成立了"必须走 `作废` 字段，避免旧结论永远挂在状态里。
- **永不碰正在进行的那一轮**。只处理已经有 `turn/end` 的轮次。

### L4 校验合并规则（v3，2026-10-25）

上一版只做"形状校验 + 守恒"，但**工程属性一条都没验**。实测拿同一个变更集应用两次：

```
一次: 待办=['写定稿清单','新任务'] 已完成=['补S02素材']
二次: 待办=['新任务']             已完成=['补S02素材','写定稿清单']   ← 不该完成的也被标了
二次 check_changes: []   二次 validate_state: []                     ← 双双放行
```

对照业界：[RFC 6902](https://www.rfc-editor.org/info/rfc6902/) 有 `test` 前置条件操作并要求**全或无**；
[幂等性实践](https://temporal.io/blog/idempotency-and-durable-execution) 指出"绝对赋值幂等、相对变更不幂等"；
[乐观并发](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) 靠 version 检测过期写入。

| 改动 | 说明 |
|---|---|
| **前置条件** | `完成/作废` 从 `[0]` 改为 `[{"idx":0,"expect":"补 S02 素材"}]`，应用前比对原文，不符即拒绝（等价 RFC 6902 的 `test`） |
| **fail-closed** | 越界下标、格式错误、expect 不符一律 `raise ValueError`，不再静默跳过（旧行为等于允许半应用） |
| **基准哈希** | 变更集带 `base_hash`（state 的 sha256 前 8 位），`check_changes`/`apply_changes` 都校验；游标也记 `state_hash` |
| **两阶段提交** | 先落 `pending` 游标 → 写状态 → 落定游标；崩在中途时启动按哈希判断：写得进就只补游标**不重放**，没写进就重做 |
| **变更集存档** | 每轮落 `第N轮.changes.json`，出问题能回溯"这轮到底改了什么" |
| **跨列表不变量** | 同一条不得同时在 待办 与 已完成；被 待办/红线/决定 引用到的锚点不许消失 |

顺带根治了 P-012（人工改状态导致下标错位）：expect 对不上直接拒绝，而不是静默错配。

验收：`test_l4_v3.py` 29 条断言（双应用被拒、expect 不符被拒、哈希不符被拒、裸整数下标被拒、跨列表重复被报）。
契约测试（2026-10-26）：`test_schema_contract.py` 锁定 `changeset_schema.json` 与
`l4_v3_27b` 的顶层/嵌套键、`目标 required` 一致（4/4，含负向漂移夹具）。

### L3 变更集规则（v2，2026-10-25）

上一版是"提示词 + `format: json` + 事后校验"，在 16 块输入下**模型漂回了扁平的旧 schema**
（顶层直接出 `完成/作废/新增待办/…`），`check_changes` 抓到了、带问题清单重问一次仍漂 —— 合并整轮失败。
查证后确认可根治：Ollama 0.40.8 支持把 **JSON Schema 传给 `format`** 做约束解码
（[官方文档](https://docs.ollama.com/capabilities/structured-outputs)），形状不对的 token 在采样阶段就被禁止。
实测同一条任务：

```
schema 约束生效: 是   eval_count: 58（首探针）/ 262（16 块回归）
```

| 改动 | 说明 |
|---|---|
| **schema 约束解码** | `changeset_schema.json` 传给 `qwen_client.chat(schema=…)`；顶层只允许 目标/待办/红线/决定/锚点，`additionalProperties: false` |
| 输入瘦身 | 引文不进合并输入（锚点已承载逐字事实）；全局事实 ≤15 条；每块只留 标题/摘要/做完/未做/用户要求/事实 |
| 末尾重复硬约束 | 把"顶层键只能是这五个、待办里分完成/作废/新增"再压一遍到 USER 末尾（近因，对应 [Lost in the Middle](https://arxiv.org/abs/2307.03172)） |
| 三层防线 | schema 保形状 → `check_changes` 保下标 → `validate_state` 保守恒；重试只用来修内容，不再指望它修形状 |
| 失败降级 | 两次仍不过 → **丢掉事实证据**（换信息而不是换措辞）再试一轮 |

回归用例：`test_merge_long.py` 用 16 块合成输入直测这一条路径（修前会漂、修后 5/5）。

**上下文截断修复（2026-10-25，A）**：`qwen_client` 记录 `done_reason`；为 `length` 时抛带
`truncated` 标记的 `QwenError`，不再把截断输出塞回重试（否则 prompt 越试越大、必再截断）。
`build_merge_user` 的独立 `{anchors}` 段只放**本轮新增**锚点（state JSON 已含全量锚点，实测 69 条
重复约 1500 tokens）；`merge_budget` 估算超 `num_ctx` 时切 lean（紧凑 state JSON、摘要/清单截断、
去 facts、输出上限 600），截断后按 lean 重建再试一次。真实 merge 复验（turn 45）：旧 lean prompt
7869 → 新 compact lean **6567 tokens**，`done_reason=stop`、7 块、193s、rc=0。

### L2 分段摘要规则（v3，2026-10-25）

旧版三个病：`facts` 写死最多 3 条（实测九块**全部正好 3 条**，等于恒定截断）、每块只有 1 条引文
（事实落地覆盖率太低）、二次失败没有降级路径。业界对照：map/reduce 与 iterative refinement 两条路
（[Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/long-document-summarization-with-workflows-and-gemini-models)），
固定分块会切断语义依赖（[Pinecone](https://www.pinecone.io/learn/chunking-strategies/)），
摘要里不被原文支持的片段都算幻觉、要靠抽取式回查（[PMC](https://pmc.ncbi.nlm.nih.gov/articles/PMC12796222/)）。

| 改动 | 说明 |
|---|---|
| `facts` 上限按块缩放 | 普通块 `max(3, min(6, 块字数 // 1200))`（3000 字→3，4800→4，6000→5）；**降级拆分出来的块用更高地板** `max(4, min(6, //900))`——拆分块本来就短，按普通口径会恒定只给 3 条 |
| `summary` 上限 220 → **300** | 先保召回再提精度（Anthropic 的压实建议） |
| 引文 1 条 → `quotes` 最多 3 条 | 每条都要逐字回查；兼容旧的单条 `quote` 字段 |
| **引文确定性回贴** | 模型擅长挑句子、不擅长逐字抄写。归一化（NFKC + 统一弯引号 + 去空白）后找最长公共片段（≥8 字），映射回原文位置并扩到句界——**让模型"指"、代码"抄"**；状态分 `verbatim / repaired / failed` |
| **事实落地检查** | 每条 fact 必须与原文共享 ≥6 字连续片段，否则 hard fail——纯代码的抽取式回查 |
| 重试降级 | 二次仍不过 → 把该块按字符中点**对半切开**各摘一次（不再递归），仍不过就保留并标记 |
| `num_ctx` 守卫 | 上次调用 `prompt_tokens > num_ctx×0.75` 即视为溢出风险，同样走对半切 |
| 跨块事实去重 | 构建合并输入时按归一化键去重，另附一段「全局事实」给 L3 |

提示词也换了（`sum_prompt_v4.txt`）：`{chunk_chars}`/`{max_facts}`/`{max_summary}` 三个占位符由程序填，
并在 SYSTEM 里要求"facts 必须是能从原文找到的短句""quotes 必须逐字"。

实测口径（待补本轮数据）：块数、facts 条数分布、quotes 条数、硬检查未过块数、触发降级块数。

**facts 配额实测（2026-10-25，P-016 审查）**：缓存 18/18 个块的 facts 条数都恰好等于当时上限
（104 轮全 3、113 轮 3/3、119 轮 4/4/4/3、120 轮 4/4/3）——**cap 是硬约束，不是软建议**。
所以 `max(3, min(6, 字数//1200))` 在 2500–3899 字恒为 3；拆分块实测（2986 字）cap=3 给 3 条、
cap=5 给 5 条，多出的 2 条都过了 ≥6 字落地检查，而「除数改 900」对 2986 字仍是 3——必须给
拆分块单独抬地板（`max(4, min(6, 字数//900))`）。另：L3 的「全局事实」按块序取前 15 条，
第 104 轮 9 块时后 4 块零覆盖，已登记 P-042。详见
审查报告。

### L1 锚点规则（v2，2026-10-25 按业界做法重写）

旧版只抽"shell 命令 + 错误尾部"，把**路径**整个漏掉了——而实测本会话里有 **748 次工具调用**
明确带着 `file_path`/`path`，工具结果 `meta` 里还有 `path 670 次`、`files 37 次`（带行号）、
`diffs 363 次`。dsh-dcp 的确定性抽取口径是"逐字路径/命令/错误/待办/用户原话"，
Claude Code 的压实清单同样要求"改过哪些文件、约束条件、活跃错误"。所以改成六类 + 配额：

| 类型 | 来源（结构化优先） | 配额 |
|---|---|---|
| `路径` | 调用参数 `file_path`/`path`/`paths`；结果 `meta.path` / `meta.paths` / `meta.files[].path`（带首个命中行号） | 12 |
| `编辑` | 结果 `meta.operation` 或 `meta.diffs` 存在时的 `meta.path` | 8 |
| `CMD` | `pwsh`/`bash` 的 `command` 首行**自适应**（≤50 原样；超出取头 35 + `…` + 尾 15）+ 多行标 `(+N 行)` + 说明吃剩余空间，整行 ≤90；**说明被截断要带 `…`**（P-062）、**行宽按显示列算**（P-063）、**标记计入预算**（P-060） | 6 |
| `ERR` | 错误结果**末尾 200 字**，按"最后一行"归一去重 | 4 |
| `要求` | 用户消息里含约束词（不许/不要/都要/必须/一律/禁止…）的句子，≤80 字 | 4 |
| `CALL` | 非 shell 工具的**首个有效参数值**（跳过 old_string/content 这类噪声键）；没有有效值就不产出 | 6 |

兜底：一条结构化路径都没抽到时，才用正则扫描用户/助手文本找 `xxx.py` 这类片段
（字符类必须含中文，否则 `02_文档/项目说明.md` 会被切成 `/x.py`）。

输出仍是 `list[str]`，每行 `类型 值`，顺序固定为 路径→编辑→CMD→ERR→要求→CALL。
判重走 `norm_key`：空白折叠；路径类另做反斜杠→正斜杠、去引号与尾标点、**合并连续斜杠、剥除 `./`、折叠大小写**；ERR 类取最后一行。
跨轮判重走 `anchor_norm(锚点字符串)`（拆出类型后套 `norm_key`），由 L4 `apply_changes` 新增锚点时使用——
同一条路径的 `\` 与 `/`、大小写、`//`、`./` 变体只保留首次出现的原文形态（P-011）。

驱动层再加一道**确定性后处理**（`tidy_anchors`）：绝对路径按项目根相对化（逐字原则不变，
只换前缀）、丢弃临时目录路径、丢弃 `x.py` 这类碎片。

实测（同一份日志）：第 110 轮 13 条 → **25 条**，其中 7 条路径 + 7 条编辑是旧版完全没有的。

> **P-059 落地审查**（报告，2026-10-25）：真机 1046 条命令，0 条超 90 码点、长命令尾部 616/616 保留、多行 632/632 带标记；
> 但 966/1046 条说明被**静默截断**（平均丢 17.2 字、无省略号），985/1046 行超 90 **显示列**（最长 119），且整行硬上限回退分支结构性不可达。
> 三个口径分别对应 P-062（省略号）、P-063（显示列）、P-060（标记预算）。

### L0 瘦身规则（v2，2026-10-25 按业界做法重写）

旧版一刀切"工具结果只留头 500 字"，被证伪：**报错和结论都在尾部**，拦腰砍掉等于把最值钱的信息扔掉。
对照的三份同题答卷：DSH 自带的 `tool-result-pruner`（8192 阈值 / head 4096 / tail 1024）、
Codex（~10 KiB / 256 行 head+tail）、pydantic-ai-harness（head_tail 2:3，且 `run_shell` 单独配 `tail`）。

| 规则 | 做法 |
|---|---|
| 头尾保留 | 超预算时保留头尾、中间换成 `…[截断 中间N字符 · 见 seq M]`（指针可回原始日志） |
| 按工具分配 | `pwsh/bash` → 头 25% / 尾 75%；`read/grep/glob` → 头 75% / 尾 25%；其它 → 40/60 |
| 错误优待 | `isError` → 头尾各一半（4000 预算下各 2000），报错信息不许被砍 |
| 去重 | 工具结果文本归一化（压空白+小写）后相同、且长度 ≥200 → 第二次起只写 `【结果 重复】同 seq M` |
| 过期淘汰 | 同工具 + 同参数再次调用的，旧结果写 `【结果 已过期】被 seq M 取代` |
| 用户消息 | **绝不截断**；超长时按前缀留白切成 `【用户 i/n】` 多段 |
| 图片 | 不计数就丢信息；行尾追加 ` · 图片N张`，纯图片结果写 `（仅图片）` |
| 错误锚点 | `ERR` 取**末尾 200 字**（异常类型在尾部），不再取开头 |

**预算怎么定**：消费者不同，预算不该相同。DSH 的 pruner 服务**活上下文**（模型要照着细节干活），给 8192；
我们的 L0 服务**摘要模型**（只要事实），所以默认 `--l0-budget 2000`。实测同一轮：

| 版本 | 行数 | 字数 |
|---|---|---|
| 旧 L0（500 字，只留头） | 14 | 6,677 |
| 新 L0 budget=1000 | 14 | 8,373 |
| **新 L0 budget=2000（默认）** | 14 | 11,373 |
| 新 L0 budget=4000 | 14 | 17,372 |

31 条断言（`test_slim_v2.py`）锁住这些行为，重点是"错误行的尾部必须出现 AssertionError"、
"用户长消息还原后与原文逐字相同"、"在用旧结果被标过期"。

### 垃圾回收（L5）

状态里的四个列表只增不减：锚点每轮最多新增 30 条，已完成、决定同样会堆积。**压缩产物自己会变成
新的上下文泄漏**——`状态.json` 是每轮都要整份喂给模型的，涨到几十 KB 就是成本线性上涨 + 注意力稀释。

L5 负责回收，原则只有一条：**回收必须可恢复**——不删内容，只把冷数据降到归档层。

#### 规则（v2，2026-10-25 按业界做法修正）

| 机制 | 做法 | 依据 |
|---|---|---|
| 预算单位 | **每个字段各自一个字符预算**（锚点 4000 / 决定 4000 / 待办 2000 / 已完成 2000），不是全局一个数 | Letta 的 memory block 各带字符上限 |
| 触发 | 某字段超预算才回收该字段，其它字段原样 | 同上（超预算但无法归因是 v1 的病） |
| 裁剪量 | 砍到该字段预算的 **70%**（滞回），不要砍到刚好贴着线 | Letta 建议只驱逐约 70% 保持连续性；砍到贴线会每轮触发 |
| 保留顺序 | 尾部保留（列表按时间追加，尾部即最近），热区保持原顺序 | — |
| 在用锚点 | 被「待办 / 红线 / 决定」引用到的锚点**强制保留**，不管多旧 | 相关性优先于时间（Generative Agents 的 recency×importance×relevance 思路） |
| 归档记录 | 每条带 `{内容, 轮次, 原因}`（决定另带理由）——能回溯 | Zep 的 episode 溯源 |
| 决定作废 | 不再直接删除：转成归档记录 `{内容, 轮次, 原因: "被取代：…"}` | Zep 的边失效：旧事实置 `t_invalid` 而非消失 |
| 检索 | `--recall <关键词>` 只把命中条目取回来，不整包搬 | Anthropic 的 JIT 检索 |

`recall()` 就是这条"归档不是黑洞"的出口：

```powershell
.\.venv\Scripts\python.exe src\_试作\compact_context.py --recall bench_power
# [锚点] 第105轮 超预算
#     src\bench_power.py
```

**回收全程不走模型**，全是确定性规则，所以它不会漂；配套的 `verify_gc_v2` 做守恒：

```
归档 + 热区  ==  回收前的完整列表（按内容多重集比较）
未被回收的字段 必须一字不动（含顺序）
prev 里被引用的锚点 必须仍在热区
目标、红线 必须原样不动
归档记录必须带轮次
```

任何一条对不上就拒绝采用、拒绝写盘。这样"回收"不可能变成"悄悄删除"。

### 为什么"把规则写细"没用

第一版把 `完成/作废` 做成**按文字匹配**，在 system prompt 里尽力写规则。实测两轮都失败：

| 版本 | 已完成 | 待办 | 红线 |
|---|---|---|---|
| v1 | 空 | 3 条陈旧 | 混进技术决定 |
| v2（加了一堆规则） | **还是空** | **6 条，全是本轮已做完的事**（把过程日志当待办） | 还是混进技术决定 |

原因不是 prompt 不够狠：**"待办 vs 已完成"是时间性判断**，而摘要通篇是过去式叙述（"把 X 做完了"），
模型分不出 X 属于哪边，于是要么全塞待办、要么全不放。

改成三件事后，同一份素材从 9/10 直接到 **10/10**：

1. **完成/作废改成引用序号**（`"完成": [0, 2]`）——模型不做分类，只做选择题；
2. **USER 模板改成问卷**（"上一版待办里哪几条做完了？只写序号"）；
3. **给合并步骤写记分牌**（`test_merge.py`，固定素材 + 10 条断言），改 prompt 前后各跑一次就有分数。

第 3 条是关键：没有它，v1→v2 那一轮就是白跑的（"看起来更规范了"，实测更差）。

### 冷启动是另一回事

序号制只在**有上一版状态**时有效。第一次压缩（空状态）没有序号可选，模型只能从散文里判断
"哪件事做完了"——又回到它做不了的那件事。实测空状态跑第 104 轮：

```
已完成: []          ← 空
待办:   5 条，全是本轮已经做完的事（"分析会话日志结构"、"委派27B执行L0并验收"…）
红线:   []          ← 用户这一轮明明提了要求
```

解法不是再改合并 prompt，而是**把分类前移到 L2**：每块摘要只覆盖约 6000 字、证据就在眼前，
让它顺手产出三个字段：

```json
{"title": "...", "summary": "...", "facts": [...], "quote": "...",
 "做完": ["本块里明确做完的事"], "未做": ["明确还没做完的"], "用户要求": ["用户明确提的要求/禁止"]}
```

这是**局部抽取**（有依据、可机器检查），不是**全局分类**（无依据、只能猜）。L3 拿到的就是
"做完/未做/用户要求"三张清单，合并退化成去重 + 归类，不再需要模型做判断。

`test_sum.py` 是这一步的记分牌（10 条断言：取消项不许混进未做、用户要求里不许混技术结论、
引文必须逐字存在……）。首版 9/10，把"取消≠未做"这条反馈回去后 10/10。

### 冷启动规则（v2，2026-10-25 已修）

冷启动原来是**拿增量协议做全量初始化**：合并问卷 5 问里 2 问是"上一版待办哪几条做完了"，
空状态下没有选项，模型只能把本轮做完的事塞进待办——实测 `已完成=[]`、`待办=5 条全是已完成事项`。

对照业界：冷启动是**初始化**问题（[Atlan](https://atlan.com/know/ai-agent-cold-start-problem/)），
状态本质是事件的**投影**、可从事件确定性重建（[eventsourcing 教程](https://eventsourcing.readthedocs.io/en/latest/topics/tutorial/part4.html)、[Marten](https://martendb.io/events/learning.html)），
而 replay 与 snapshot 是持久 agent 的两条正路。所以我们改成"投影 + 两道判断题"：

| 字段 | 来源 |
|---|---|
| 已完成 | 各块 `做完` 的并集（去重保序） |
| 待办 | 各块 `未做` 的并集 **减去** 已完成的条目（按归一化文本比对） |
| 红线 | 各块 `用户要求` 的并集 |
| 锚点 | 本轮锚点（去重） |
| 目标 / 决定 | 模型只回答这两项（独立小提示词 + `coldstart_schema.json` 约束解码） |

校验由 `check_cold` 负责：已完成必须覆盖全部 `做完`、待办必须是 `未做` 的子集、两栏不得相交、
红线必须覆盖全部 `用户要求`；任何一条不过就整轮中止。

实测：

| 场景 | 结果 |
|---|---|
| 第 104 轮离线投影（9 块） | 已完成 31 / 待办 17 / 红线 7，`check_cold` 通过（旧版是 0 / 5） |
| 第 120 轮真机冷启动（3 块） | 已完成 15 / 待办 4 / 红线 3 / 决定 2，目标由模型给出 |

已知残留（P-035）：`未做` 是**按块局部抽取**的，早期块说"还没做"的事可能在后续块被做完，
投影时会留在待办里。下一步用后续块的 `做完` 做模糊包含匹配剔除。

## 4. 机器检查

| 层 | 检查 | 不过怎么办 |
|---|---|---|
| L2 | `summary_nonempty` / `summary_independent`（无"如前所述"类前指代）/ `summary_no_guess`（无推断词）/ `quote_verbatim`（引文逐字回原文） | hard 失败 → 带原因重写这一块，一次 |
| L2 | `summary_length` ≤220 字 | soft，只记录不重试 |
| L4 | `validate_state`：字段不丢、锚点不丢、无重复项、决定内容非空、类型正确 | 带问题清单重问一次，仍不过就整轮中止并记日志 |
| L5 | `verify_gc_v2`：归档 + 热区多重集必须等于回收前、未回收字段一字不动、在用锚点不许回收、目标红线不许改、归档记录必须带轮次 | 拒绝采用回收结果，保留原状态 |

## 6. 和 `rolling_summary` 的关系

同一套"分段 + 不递归 + 每段独立"的思路，但目标不同，不能互换：

- `rolling_summary` 压**文章内容**，产出给写作回忆用，要求每段独立成文（所以禁前指代）。
- 本方案压**会话状态**，产出给接手的人/模型用，必须有跨轮累积（所以有状态层 + 作废）。
