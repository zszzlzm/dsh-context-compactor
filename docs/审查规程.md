# 实现审查（`impl_audit`）

> 这是**派给在线模型自己**的任务类型：查业界怎么做、把我们自己的实现拆成功能逐个校对、给判定和修复方案。
> 与 [委托协议](委托协议.md) §3 里那些"派给本地 27B 的预设"是两回事——那类是外包劳动，这类是必须我来做的判断。
> 配套工具：`src/audit.py`；产物放 `02_文档/审查/`。

## 1. 什么时候用

- 用户说"查查网上这方面怎么解决""校对一下目前的实现算不算优秀""把实现拆成功能一个个查"
- 一个子系统刚做完、要进入下一阶段前的自检
- 某个问题反复出现，怀疑是设计层面不对（而不是某个 bug）

不适用：单点 bug 修复（走问题清单）、纯代码实现（走委托协议 §8 派给 27B）。

## 2. 任务类型卡

| 项 | 值 |
|---|---|
| task_type | `impl_audit` |
| 中文叫法 | **实现审查**（也常被说成：对照审查、逐功能审查、体检） |
| 执行者 | 在线模型（我）；**不派给本地模型** |
| 输入 | 一个实现：代码文件 + 提示词 + 真实运行日志 + 现有断言 |
| 输出 | `02_文档/审查/<日期>_<主题>.md`，六小节四张表 |
| 硬检查 | `audit.py check`：六小节齐全、逐功能表 ≥5 行且判定 A–F、总评有"总体判定"、提案表三列非空、证据含代码块、收尾写了问题清单动作 |
| 耗时 | 15–40 分钟（联网查证 + 实测） |

## 3. 七个步骤

1. **拆功能**：先把实现拆成可独立评价的功能点（一个函数、一条规则、一个策略算一条），
   列出 F1…Fn 之后再开始查——不允许"边查边想拆哪些"。
2. **先找现成，再查业界**：
   - 找现成：把功能点映射到已有库/工具（标准库、PyPI、系统命令），至少列 2 个候选，
     记录许可证、体积、依赖、是否已安装/可安装、覆盖度；
   - 查业界：每个功能点至少检索一次；优先 RFC / 官方文档 / 论文，其次工程博客；
   - 必须给 **adopt / adopt+wrap / build** 的三选一结论与理由；给不出理由的自建按不合格处理。
   记录**出处链接**，最后汇总成「业界做法」表。
3. **实测**：能跑的一律跑，留下命令与输出（数字优先）；不能跑的写清原因。
   **没有实测的审查不算完成。**
   候选也要实测：能装的装、wheel 能直接 zip 导入的就导入，留下命令与输出；装不上要写清原因（网络/许可/体积）。
   **禁止心算**：报告里每个数字都必须来自脚本输出（命令贴进证据节）；总数、百分比、范围一律由程序算，
   每份报告配 `verify_<主题>_numbers.py` 数字账，全 MATCH 才算完成。
   数字口径统一走 `src/num.py`：`eval` / `pct` / `agg` / `unit`（mW→W、GB→GiB 等）/ `date`（时长差）；
   `--save` 追加 `06_日志/num_calls.jsonl` 留痕；账本脚本可 `import num` 或直接调 CLI。
4. **逐条判定**：A/B/C/D（可带 +/-），每条给依据（实测数字或出处）。
5. **总评**：总体判定 + 分维度评价（语义设计 / 强制力 / 韧性 / 可回溯 等）。
6. **提案**：每条写「改动 / 依据 / 验收」，验收必须是**可数断言**（"新增 N 条断言""双应用必须被拒"）。
7. **收尾**：问题清单登记或关闭（`issues.py`）；文档回填（把结论写进对应流程文档）；
   报告骨架过 `audit.py check`。

## 4. 判定标准

| 判定 | 含义 |
|---|---|
| **A 优秀** | 有实测支撑、边界清楚、有机器校验兜底 |
| **B 合格** | 方向对，个别处可改进 |
| **C 及格偏下** | 能跑，但有关键缺口（缺校验、缺降级、缺实测） |
| **D 不合格** | 会产生错误数据或静默失败 |
| **C?** | 缺实测、无法判定——必须写明缺什么实测，**不允许只写"看起来可以"** |

## 5. 反模式（都是我踩过的）

- **只查不测**：查完资料就下结论，结果"看起来更规范了"实测更差（L3 prompt v1→v2 就是）。
- **先自己写再查资料**：写完才想起有没有现成库，等于把选型题做成实现题。先看标准库/PyPI/系统命令，再决定要不要写。
- **只列功能不给判定**：读起来很长，但没有可比较的结论。
- **提案没有验收**：改完无从验证，下轮还得靠眼看。
- **把已修复的坑当新问题查**：先 `issues.py list --all` 对照。
- **把业界建议当"必须改"**：要结合本项目语境（例如 DSH pruner 给 8192 是因为它服务活上下文，
  我们服务摘要模型，2000 就够）——理由写在依据列。

## 6. 报告骨架

`audit.py start --topic "L2 分段摘要" --layer L2` 生成骨架；填完跑
`audit.py check 02_文档/审查/<文件>.md`，非 0 就是不合契约。

报告头部除层/日期/执行者外，还要写一行 `数字账：<verify 脚本路径>`（对应 AGENTS §6.5）。
**新报告必须过 `audit.py check --strict`**：数字账要声明、存在、且被实际执行并通过（退出码 0）；
历史报告可写 `数字账：wontfix（原因）` 豁免，但必须在 `02_文档/审查/豁免清单.txt` 登记
（新报告不得豁免），迁移见 P-047。

模板固定六小节：业界做法 / 逐功能判定 / 总评 / 修复提案 / 证据与复现 / 收尾。

## 7. 数字账原则（2026-10-25 起）

- **账本不重造测量**：静态事实自己数源码；行为事实**一律 subprocess 调用已有脚本**
  （`probe_*.py`、`test_*.py`），解析它们的输出。同一件事只允许一份测量实现。
- 反例：让模型在账本里内联再写一遍死端口探测——两边实现会漂，账本变成"自己证明自己"。
- 测量脚本要输出**稳定的机器可读字段**（如 `has_start_hint`），不要依赖截断后的文本片段。
- 报告头部的 `数字账：` 声明必须指向真实存在、可重跑、退出码 0 的脚本；历史快照类报告用
  `数字账：wontfix（原因）` 并在 `02_文档/审查/豁免清单.txt` 登记。
- **头部不要手写账本条数**（如“（12 MATCH / 0 MISMATCH）”）：条数以账本输出为准，重跑会变；
  `audit.py check --strict` 会直接拒绝手写条数（P-061）。
- 数字工具：`num.py` 是唯一数字口径工具（simpleeval 求值 / pint 单位 / dateutil 日期）；
  单位换算、时长差不要心算，优先用它并可用 `--save` 留痕。
